# Unified resumable invocation runtime — implementation status (superseded)

> **Superseded by the workflow VM cutover.** The invocation subsystem this documents was removed
> rather than switched on: `workflow_invocations`/`workflow_invocation_calls`, `InvocationStore`,
> `WorkflowNodeKind::Invocation`, the invocation node operation, `invocation_migration`,
> `CompileOptions::emit_invocations`, and `invocation_call_id` on the broker are all gone. The
> resumable-continuation idea it was reaching for is now the whole runtime — see
> [the Phase 14 cutover record](workflow-vm-phase14-readiness.md) — so the two-switch deployment
> sequence below never ran and is kept only as a record of the reasoning.
>
> `runinator-compute`'s VM, catalog, assembler, and operator intrinsics survive; they are what the
> workflow VM uses for invocation frames.

`unified-resumable-invocation-runtime-plan.md` is the design. This is what was built, what was
deliberately gated, and what the cutover would have required from an operator.

## What is deliberately not switched on

Two switches are off, and they are the same decision seen from two sides.

`CompileOptions::emit_invocations` decides whether a newly compiled `do { }` block becomes an
`invocation` node or a `std.run`/`std.exec` node. `invocation_migration::convert_definitions`
rewrites the definitions already stored. Neither is a preference — together they change what a
compiled definition *is*, and a fleet cannot be half-way through that change: a replica running the
old build cannot execute an `invocation` node, and a run already in flight against the old node
shape would find its node replaced underneath it.

So the cutover is a deployment sequence, not a code change:

1. Deploy this build everywhere. Every replica can now *execute* invocations; none produce them.
2. Drain to zero non-terminal runs. In-flight runs are pinned to their `workflow_snapshot`, so this
   is what makes the rewrite safe rather than a data-migration problem.
3. `invocation_migration::preflight` — a read-only pass reporting, per definition, whether it would
   convert. Any blocked definition aborts the whole migration; a partially converted fleet is a
   state the converter will not produce.
4. `invocation_migration::convert_definitions` once the preflight is clear.
5. Turn on `emit_invocations` so newly compiled packs match what is now stored.

Step 3 is the one worth not skipping. It answers "would *every* definition convert?" before any of
them have been rewritten, which is the only point at which the answer "all but one" is actionable.

## What the plan called for and this does differently

- **An invocation node keeps the authored statement tree beside its bytecode.** The plan has the
  module alone. Recovering `let`/`if`/`return` from a flat instruction stream is control-flow
  reconstruction, and the editor pane is regenerated by decompiling — so a decompiler that was not
  exactly right would silently rewrite the author's code on save. Retaining the source is the same
  arrangement `metadata.rexrap.functions` already uses for signatures.
- **`std.code` is not converted to a one-call invocation.** It has no program to assemble, and the
  node already dispatches exactly once and settles; converting it would lose the container
  configuration and buy nothing.
- **`goto` stays**, per the operator's decision, as a fourth `InvocationStep` outcome.
- **Secrets force the whole invocation worker-side.** `secret.a.b` lowers to the literal string
  `secret://a/b` and only the worker substitutes it, so an in-process `upper(secret.x)` would
  uppercase the placeholder and return garbage. The VM yields unconditionally on any call whose
  arguments contain a secret placeholder.
- **The legacy execution paths are still present.** The plan deletes them as the last commit of the
  cutover. They cannot be deleted before step 4 above has actually run somewhere, because until then
  they are what executes every stored definition.

## Not yet done

- Runtime/debug APIs do not yet surface invocation calls as children of their authored node, so a
  suspended stack is inspectable in the database but not through the API.
- The command center renders an `invocation` node from the backend catalog, but has no per-call
  timeline view.
- `docs/unified-resumable-invocation-runtime-plan.md` still describes `compute`/`std.run`/`std.exec`
  as present, which they are.
